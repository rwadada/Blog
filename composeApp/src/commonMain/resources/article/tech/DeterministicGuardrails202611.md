# AI DLCやSkillを作り込むのをやめて、決定論的ガードレールに全振りした話

3ヶ月前に書いた記事「AIコーディングツールとの付き合い方、現時点での個人的な所感」では、AIコーディングのボトルネックが「実装」から「レビューと検証」へ移動したこと、そして大量のAI製ドキュメントの査読や質問攻めが人間の認知限界（レビュー疲れ）を超えることについて書きました。

あの時点では「役割別のレビュー用エージェントや Skill を定義して、影響範囲に応じてレビューの厚みを変えるしかないかな（正直まだ探り中）」と締めくくっていました。

あれから3ヶ月、個人開発のプロダクトをゴリゴリ作り込みつつ、流行りの **AI-DLC（AI-Driven Development Life Cycle）** や **Spec駆動開発**、**LLM Wiki**、細かく作り込んだ **Skill** も一通り触ってみた結果、**当時は想定していなかった別の結論**に辿り着きました。

正直に言うと、AI-DLC や LLM Wiki、重厚な Skill 作り込みは**どうしても肌に合いませんでした。**  
実際に運用してみると、3ヶ月前に感じていた「レビュー疲れ」に加えて、以下のペインが次々と襲ってくるからです。

- **重厚なドキュメントが大量生成されるが読みきれない**（人間の認知限界を超える）
- **最初に要件を決め切るため、実装中にコードベースと齟齬が出たときの遡及が大変**
- **結局、生成されたコードの正しさは人力で測らなければいけない**
- **定期的にコンテキスト（プロンプト・設計書）が腐る**
- **LLM Wiki のデータもコードから乖離して腐る**
- **複数人（あるいは複数エージェント）で扱うとドキュメントがコンフリクトの山になる**

じゃあ今自分はどうしているのかというと、**ガチガチの Skill や重厚な事前ドキュメント、AI同士のレビューの重ね掛けはやめました。**  
代わりに、**型・Linter・アーキテクチャテスト・仕様書自動生成・CI・実行ハーネス（Hook / worktree 隔離）といった「決定論的な仕組み」で規約と動作と行動境界を機械的に担保し、本当に対応してもらいたい実装や探索に AI のパワーを全振りする**運用にしています。

この記事では、3ヶ月前の「レビューボトルネック」「コンテキストノイズ」「綺麗なコードベースの維持」という課題意識を踏まえた上で、なぜ自然言語でAIを縛るアプローチがしんどくなるのかを整理し、個人開発アプリ（Tripolio）での実践例、そして **AWS公式の AI-DLC（`awslabs/aidlc-workflows` v2.11.4）** と **決定論的ガードレール運用** を同一条件でぶつけた比較実験の結果をまとめます。

## 1. なぜ「AI DLC / LLM Wiki / 重厚Skill」はしんどくなるのか

個別のツールの出来が悪いわけではありません。構造的な問題がひとつあります。

> **確率的に動く AI の出力を、さらに曖昧で非決定論的な「自然言語（ドキュメント・Wiki・Skill）」で縛ろうとしている。**

自然言語で書いたルールや設計書には、以下の宿命があります。

1. **嘘をついてもエラーが出ない**: コードが変わっても Markdown は赤くならない。気づいたときには Wiki も設計書も「化石」になっている。
2. **コンテキストノイズを増やす**: 前回の記事でも触れた Lost in the Middle の問題と同じで、分厚いドキュメントや長大な Skill を読ませ続けるほど、本当に重要な指示が埋もれ、トークンと時間も消費する。
3. **集中管理ファイルは並列開発で必ず衝突する**: `requirements.md` や `tasks.md`、Wiki のインデックスに複数ブランチから追記すれば、コードがどれだけ疎結合でもドキュメントがコンフリクトする。
4. **「守れているか」の検証コストが人間に残る**: AI が「規約をすべて遵守しました」と報告しても、本当にそうかは人間が目視するまで確信できない。前回の記事で触れた「過信バイアス（Overconfidence Gap）」の温床にもなる。

「ドキュメントや Wiki は腐る。でもコンパイラとテストは嘘をつかない（腐ったら落ちる）」。  
ここを割り切って、**決定論的に判定できることはすべてコード・テスト・ハーネスに逃がす**のが、3ヶ月前に「探り中」だったレビューボトルネックに対する自分なりの答えです。

## 2. 自分の運用例: 決定論的ガードレールの4層構成

前回の記事で「AIに良いコードを書かせる最大の要素は、小手先の指示文ではなく、リポジトリ内にある統一感のある綺麗なコードベースそのもの（最強の Few-shot）」と書きました。

ただ、開発が進むと人間の気合いだけではその統一感を維持できません。そこで、自分が個人開発している旅行アプリ **Tripolio** では、普通なら長大な Skill や Wiki、レビューチェックリストに書きがちな内容を、以下の4層の「落ちるテスト・自動生成・ハーネス」に置き換えています。

### 2.1 アーキテクチャ・規約の静的テスト

通常のテストスイートの一部として走るアーキテクチャテストで、コードベースの統一感を機械的に強制しています。

- **レイヤー依存の向き**: ドメイン層の純粋性や、UI 層からデータ層・外部 SDK への直接参照を禁止
- **型による状態強制と単方向データフロー**: 画面の状態は直和型（sealed class 等）で表現させ、boolean フラグの組み合わせを禁止
- **デザインシステム強制**: 生の色コードや文字スタイル、余白の数値直書きを禁止
- **過去バグの再発防止と本番汚染防止**: 一度踏んだ落とし穴や、開発用コードの本番ビルドへの混入を静的ルール化
- **検出器自体の自己検査テスト**: テストの空振り防止まで含める

これがあるおかげで、**「AIにとって最強のお手本となる綺麗なコードベース」が人間のレビュー負荷ゼロで維持され続けます。**

### 2.2 仕様書は手で書かない -> コードからの自動生成

画面やデザインの仕様書は **手編集禁止** とし、コードと UI プレビューから自動生成する仕組みにしています。さらに CI でドキュメント漏れやプレビューの網羅性まで検査するため、仕様書がコードから乖離しようがありません。

### 2.3 E2E の腐敗すら単体テストで捕まえる

E2E テストのシナリオが参照している画面文言・識別子がアプリコードに実在するかを、**PR の単体テスト時点で検査**します。文言変更で夜間の E2E が密かに壊れるのを防ぐ仕組みです。

### 2.4 エージェントの行動境界すらハーネスで止める -> Hook + worktree 隔離

決定論的なガードレールは、コードやテストだけでなく**AI エージェントの実行ハーネス層**にも広げています。

以前は「PR を勝手にマージしない」「保護ブランチに直接 push しない」「本番環境を触らない」「worktree 間で衝突する操作をしない」といった禁止事項を文章で書いていました。今はこれらを**文章の頼みではなく仕組みで止めています**。

- **worktree 隔離をエージェント定義で固定**: 呼ぶ側の「付け忘れ」で共有作業ツリーを触ってしまう事故を物理的に防ぐ
- **実行前 Hook で危険操作をブロック**: コマンド実行前にスクリプトが検査し、禁止操作ならエラーコードと理由を返して機械的に止める
- **Hook 自体も CI でテストする**: 「止めるべきコマンド」と「通すべきコマンド」を毎回 CI で検証し、ガードレール自体の腐敗も防ぐ
- **エージェントの記憶はリポジトリに置かない**: リポジトリ内管理にすると worktree 隔離と相性が悪く、PR に関係のない変更やコンフリクトの種が混ざるため、ユーザー領域に逃がしています

### 2.5 その結果、AI に渡す自然言語コンテキストは極限まで薄い

こうした決定論的なガードレールを敷き詰めた結果、AI 向けの自然言語ドキュメントは驚くほど薄く保てています。

- プロジェクト共通のガイドは要点とリンク集だけの薄い構成
- プロジェクト固有の Skill も、定型的な相談・分析や探索テストなど必要最小限の数個だけ

しかも AI による探索テストは**「合否判定には使わない」**と明確に役割を分離しています。合否は決定論的テストに任せ、AI は「実装」と「未知の穴探し」という非決定論的な強みだけに集中させる設計です。

## 3. 比較実験: AWS公式 AI-DLC vs 決定論的ガードレール

「そうは言っても本当に差が出るの？」を確かめるため、実際に同じミニアプリで比較実験を行いました。  
実験に使用したリポジトリと全ブランチの成果物は GitHub に公開しています。ブランチを切り替えることで、共通スターター（`main`）・A案（`pattern-a` / `pattern-a-4b`）・B案（`pattern-b`）の実コードとマージコンフリクトをそのまま手元で再現できます。

- **検証リポジトリ**: [rwadada/ai-dlc-vs-deterministic-exp](https://github.com/rwadada/ai-dlc-vs-deterministic-exp)（[A案: `pattern-a`](https://github.com/rwadada/ai-dlc-vs-deterministic-exp/tree/pattern-a) / [B案: `pattern-b`](https://github.com/rwadada/ai-dlc-vs-deterministic-exp/tree/pattern-b)）

### 実験条件（フェアネス重視）

藁人形論法にならないよう、A案には自作のなんちゃってワークフローではなく **AWS 公式の [`awslabs/aidlc-workflows` (v2.11.4)](https://github.com/awslabs/aidlc-workflows)** を公式手順どおり導入し、公式の project memory（`aidlc/spaces/default/memory/project.md`）と `.claude/rules/` に規約を記載しました。

- **お題**: 旅行の割り勘・精算ミニアプリ `TripSplit`（React + Vite + TypeScript strict + Vitest）
- **同一条件**: 同一モデル、同一スターター、**完全に1対1で一致する8つの開発規約**
  1. `domain/` は純 TypeScript（React / DOM / Storage 禁止）
  2. View（`*.tsx`）から `data/` や `localStorage` を直接触らない
  3. 状態は Discriminated Union（`isLoading` / `isSettled` / `isOverdue` 等のフラグ禁止）
  4. 現在時刻は `Clock` 注入（`new Date()` / `Date.now()` 直呼び禁止）
  5. View に生の色コード（`#...`）・生 `px` を書かない（`tokens.ts` 強制）
  6. 金額計算（整数円・端数処理）は `domain/` に閉じ込める
  7. View の状態変更は `useReducer` + `dispatch`（UDF）
  8. 仕様書が最新コードと一致していること（A案はドキュメント更新、B案は `scripts/gen-spec.ts` 自動生成＋CI検証）

### 現実の開発を模擬した 4 ステップ

単なる 0 -> 1 の機能追加ではなく、運用で必ず起きるイベントを順番にぶつけました。

- **Step 1（初期実装）**: 旅行グループ作成・メンバー登録・立替記録・均等割り計算・状態遷移（`draft -> open -> settled`）
- **Step 2（仕様変更）**: 均等割りだけでなく「一部メンバー除外」「負担割合（重み）指定」＋理由入力による「精算取り消し（`settled -> open`）」
- **Step 3（規約違反誘発）**: 「精算期限」設定、現在時刻超過時の赤い警告バッジ表示、ローカル永続化・復元・初期化
- **Step 4（並列ブランチ開発 -> マージ）**: 2つの worktree で独立タスク（**4a: CSV エクスポート** / **4b: メンバー別収支サマリービュー**）を同時実装してマージ

### 計測・集計のやり方

数字の妥当性と再現性を担保するため、推定値や目算は使わず、すべての指標をログやコマンドから機械集計しています。

- **トークン消費量・ターン数**: 外部トークナイザー（tiktoken 等）による推定や文字数換算ではなく、エージェント実行基盤が各 LLM 呼び出し（`PLANNER_RESPONSE`）ごとにモデル API のレスポンスから記録した実測のトークン数（`input_tokens`・`cache_read_tokens`・`output_tokens`）およびターン数・ツール呼び出し回数を、全 10 セッションのログ（JSONL）から Python スクリプトでそのまま合算しています
- **所要時間**: 各ステップの開始時・終了時に `date +%s` で取得したウォールクロック秒数の差分（コマンド・テスト実行時間を含む）。Step 4 の 4a / 4b は並列実行していますが、総作業コストを比較するため合計時間には両方を加算しています
- **ドキュメント量**: `wc -lm`（行数・文字数）で計測しています。A案はフレームワーク本体（`.claude/` 配下の 388 ファイル）を除外し、プロジェクト固有の生成・維持文書（`aidlc/spaces/default/` 配下の `.md` / `.json`）のみを対象にしました。B案は `AGENTS.md` + `CLAUDE.md` + `docs/generated/spec.md` を同様に計測しています
- **規約違反の交差検証**: Step 4 完了後、B案で使った静的検査テスト（`tests/architecture.test.ts`・9テスト、検出器の自己検査 1 件を含む）を A案の最終コードへそのままコピーして `vitest run` を実行し、すり抜け件数を機械判定しています
- **並列マージコンフリクト**: 同一のベースコミットから分岐した Step 4a / 4b の 2 ブランチを順に `git merge --no-edit` し、Git が報告した `CONFLICT` ファイル数と `<<<<<<<` マーカー数をカウントしています

### 4.1 コード 1 行書く前のセットアップ時点で 80 倍の差

| 初期セットアップ指標 | A案（AWS公式 `aidlc` v2.11.4 + 規約） | B案（決定論的ガードレール） |
| --- | ---: | ---: |
| 追加ファイル数 | **398 ファイル**（`.claude/` + `aidlc/`） | **5 ファイル** |
| 追加行数 | **299,775 行** | **366 行** |

さらに、A案で公式の `feature` スコープを起動したところ、この小さな割り勘アプリに対して **全33ステージ・30承認ゲート** が組まれました。また、チェックポイント通過時に人間ターンの返答をフックで必須検証する仕組みのため、自律進行も Stage 1（`intent-capture`）で停止するほど重厚なプロセスでした。前回の記事で触れた「調整コスト（Coordination Overhead）とレビュー疲れ」が、まさに仕組みとして組み込まれている形です。

> 注記: 公式エンジンは各承認ゲートで実人間の対話入力をフックで必須検証する仕様のため、非対話の自動実行では Stage 1 で停止しました。そのため Step 1 の実装以降〜Step 4 は、AI-DLC が生成した公式ディレクトリ構造（`aidlc/spaces/default/...`）と project memory に沿ってドキュメント更新 -> 実装を回しています。仮に全 30 ゲートを人間が対話承認しながら進めた場合、所要時間・トークン消費量ともにさらに増える方向になります。

### 4.3 人間が向き合うドキュメント量は 20.7 倍、しかも初期文書は化石化

フレームワーク本体（`.claude/`）を除いた純粋なプロジェクト文書を比較すると、以下の通りになりました。

- **A案（`aidlc/spaces/default/`）**: **1,330 行 / 71,012 文字**
- **B案（`AGENTS.md` + `CLAUDE.md` + 自動生成 `spec.md`）**: **66 行 / 3,432 文字**（約 **20.7 分の 1**）

しかも A案では、Step 2〜4 で `requirements.md` や `domain-design.md` を都度書き直す一方で、Step 1 で生成された `aidlc-state.md` や `intent-statement.md` などは更新されず、**コードと食い違った「化石ドキュメント」**として残りました。  
B案は `docs/generated/spec.md` をコードから自動生成し CI（`spec:check`）で最新性を強制するため、乖離は **0件** です。

### 4.4 並列マージで「コードは衝突ゼロなのに、ドキュメント4ファイル全部が衝突した」

今回もっとも象徴的だったのが Step 4（2ブランチ並列開発 -> マージ）の結果です。

- **B案**: `git merge` 一発成功（**コンフリクト 0 件**）。マージ直後の `npm run ci`（型チェック + 全55テスト + アーキテクチャテスト + `spec:check`）も **1.00秒で PASS**。
- **A案**: **`src/` と `tests/`（コード本体）は 1 箇所もコンフリクトせず自動マージできたのに、AI-DLC のドキュメント 4 ファイルすべて（4/4 = 100%）がコンフリクト（計5箇所）してマージが停止しました。**

実際に `requirements.md` で起きたコンフリクトがこちらです。両ブランチが独立して **`FR-8`** を採番したため、真正面から衝突しました（`tasks.md` でも同様に **`Unit 13〜16`** が丸被りしました）。

```diff
<<<<<<< HEAD
### FR-8: 立替履歴・精算結果の CSV エクスポート
- FR-8.1: ユーザーは選択中の旅行グループの「グループ概要」「立替履歴」...
=======
### FR-8: メンバー別収支サマリービュー（立替合計・負担合計・最終収支の比較）
- FR-8.1: 選択中の旅行グループについて、メンバーごとの「立替合計」...
>>>>>>> pattern-a-4b
```

コードは綺麗に疎結合に書けているのに、集中管理されたドキュメントや Wiki が並列開発のボトルネックになる構造が、そのまま実測で再現されました。

### 4.5 正直な発見: 8 規約なら A案も違反 0 件だった - しかし「証明コスト」がまるで違う

最後に、B案で使った `tests/architecture.test.ts`（9テスト）を A案の最終コードに対しても実行し、規約違反のすり抜け件数を機械計測しました。

結果はなんと、**A案も 9/9 PASS（違反 0 件）**でした。

ここはフェアに認めるべきポイントです。最新世代のモデルは、規約が 8 個程度の明快なスコープであれば、自然言語のルールだけでもかなり正確に守れます。

**しかし、本質はその先にあります。**

- A案では、AI が「8規約すべて遵守しました」と自己申告してきても、**本当に守られているかを人間が目視レビューするまで確信できません。**（まさに前回の記事で書いた「過信バイアス」と「レビューボトルネック」そのものです）
- 実際、この実験で「A案も違反 0 件だった」と証明できたのは、**B案の `architecture.test.ts` を借りて 350ms で機械検証したから**です。
- そして現実のプロダクト開発では、規約は 8 個ではなく数十個以上に増え、何ヶ月も何百 PR も続きます。自然言語の遵守率はコンテキストが増えるほど確率的に落ちますが、決定論的テストは規約がどれだけ増えても毎回 100% 機械的に落としてくれます。

## 5. AI-DLC 側の主張と、それに対する自分の見解

ここまで比較実験の結果を見てきましたが、公平を期すために **AI-DLC 側が何を解決しようとしているのか** も押さえておきたいです。

AI-DLC の主張自体は、とても真っ当です。  
行き当たりばったり（Ad-hoc）な AI コーディングは、プロジェクトが大きくなるにつれて「なぜこの仕様にしたのか」「要件・設計・実装・テストがどう紐づいているのか」という文脈が急速に失われます。そこをステージ分割・承認ゲート・トレーサビリティ・監査証跡という統一プロセスで繋ぎ止めることで、大規模チームやエンタープライズ開発でも品質と説明責任を保てる、というのが AI-DLC の強みです。

また、今回の実験では標準的な `feature` スコープを使いましたが、AWS 公式 AI-DLC にもより軽量なスコープ（`express` 等）や、プロジェクトに合わせてステージ・ルールをカスタマイズする仕組みが用意されています。  
**「プロジェクトに最適化して、余計なステージやドキュメントをどんどん削ぎ落としていけば、別に悪くないのかも？」** と思う部分も正直あります。

**とはいえ、そこまで削ぎ落とすなら「本当に既製品の AI-DLC を使う必要があるのか？」という疑問が残ります。**

- 398 ファイル・約 30 万行ものフレームワークをリポジトリに抱え込んだ上で、自分たちの現場に合わせて設定やステージを削り、フックやルールの挙動を追い続けるコストは小さくない
- 余計なものを削ぎ落としていった先に残るのは、結局「薄い開発ガイド＋最小限のハーネス（Hook / worktree 隔離）＋決定論的なテスト・CI」というシンプルな構成になる
- 監査証跡や承認ゲートそのものが組織要件として必須なら既製品の AI-DLC を導入する価値は大きいが、そうでないプロダクト開発なら、最初から自分たちのリポジトリに合わせて数百行の決定論的ガードレールを育てたほうが、見通しもメンテナンス性も圧倒的に良いと感じています

## 6. この先の世界線: 重厚な Skill が不要になる開発のかたち

3ヶ月前の記事では「ボトルネックはレビューに移動した。影響範囲の見極めやレビューの自動化はまだ探り中」と書いていました。今の自分が思い描いている、この先の現実的な世界線はこうです。

- **レビュー疲れが起きない「最小限の確認」で済む開発にする**: PR は小さく保ち、人間はすべての行を追うのではなく**「判断が揺れる箇所（仕様・設計・トレードオフ）」だけを見る**。人間は**意思決定の最終責任だけを持つ**形に寄せていく
- **コード品質はすべてテスト（決定論的ガードレール）で担保する**:
  - 規約や設計制約 -> **Skill に書く前に、落ちるテスト（`architecture_test`）にする**
  - 仕様書やカタログ -> **Wiki に手書きせず、コードから自動生成して CI で鮮度を守る**
  - 過去のバグ再発防止 -> **プロンプトに追記せず、静的テストや回帰テストにする**
  - エージェントの危険操作や作業境界 -> **文章で頼まず、`PreToolUse` Hook と `isolation: worktree` で仕組みとして止める**
- **人間が本当に制御すべきは「テストの正しさが破綻しない手立て」**: コード品質をテストに委ねる以上、テスト自体が空振りしたり、AI が都合よく条件を緩めたりすると仕組み全体が崩れます。検出器の自己検査テストやテストの層分け、ガードレール自体のテストなど、**「検証の仕組みそのものの健全性」**だけは人間がしっかり握る必要があります

スピード感を持ってプロダクトを育てていく日々の開発においては、自然言語のドキュメントや Skill を厚くするほど、時間・トークン・人間の認知負荷・マージコンフリクトという負債が雪だるま式に増えていきます。決定論的なガードレールで「守るべきこと」を機械に丸投げし、テストの健全性だけを人間が制御できれば、**基本的に重厚な Skill は不要な世界が来るはず**だと考えています。

Skill をもう 100 行書き足す前に、まずは 20 行のアーキテクチャテストを 1 本書いてみるのがおすすめです。
