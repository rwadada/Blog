# AI DLCやSkillを作り込むのをやめて、決定論的ガードレールに全振りした話

最近、AIコーディング界隈では **AI-DLC（AI-Driven Development Life Cycle）** や **Spec駆動開発**、**LLM Wiki**、あるいは細かく作り込んだ **Skill** を使って開発プロセス全体をAIに管理させるアプローチが流行っています。

自分も一通り触ってみました。その上で正直に言うと、**どうしても肌に合いませんでした。**

理由はシンプルで、実際に運用してみると以下のペインが次々と襲ってくるからです。

- **重厚なドキュメントが大量生成されるが読みきれない**（人間の認知限界を超える）
- **最初に要件を決め切るため、実装中にコードベースと齟齬が出たときの遡及が大変**
- **結局、生成されたコードの正しさは人力で測らなければいけない**
- **定期的にコンテキスト（プロンプト・設計書）が腐る**
- **LLM Wiki のデータもコードから乖離して腐る**
- **複数人（あるいは複数エージェント）で扱うとドキュメントがコンフリクトの山になる**

じゃあ自分はどうしているのかというと、**ガチガチの Skill や重厚な事前ドキュメントはほぼ使っていません。**  
代わりに、**型・Linter・アーキテクチャテスト・仕様書自動生成・CI といった「決定論的な仕組み」で規約と動作を機械的に担保し、本当に対応してもらいたい実装や探索に AI のパワーを全振りする**運用にしています。

この記事では、なぜ自然言語でAIを縛るアプローチがしんどくなるのかを整理した上で、実際に自分が個人開発しているアプリ（Tripolio）での運用例を紹介し、最後に **AWS公式の AI-DLC（`awslabs/aidlc-workflows` v2.11.4）** と **決定論的ガードレール運用** を同一条件でぶつけた比較実験の結果をまとめます。

---

## 1. なぜ「AI DLC / LLM Wiki / 重厚Skill」はしんどくなるのか

個別のツールの出来が悪いわけではありません。構造的な問題がひとつあります。

> **確率的に動く AI の出力を、さらに曖昧で非決定論的な「自然言語（ドキュメント・Wiki・Skill）」で縛ろうとしている。**

自然言語で書いたルールや設計書には、以下の宿命があります。

1. **嘘をついてもエラーが出ない**: コードが変わっても Markdown は赤くならない。気づいたときには Wiki も設計書も「化石」になっている。
2. **集中管理ファイルは並列開発で必ず衝突する**: `requirements.md` や `tasks.md`、Wiki のインデックスに複数ブランチから追記すれば、コードがどれだけ疎結合でもドキュメントがコンフリクトする。
3. **「守れているか」の検証コストが人間に残る**: AI が「規約をすべて遵守しました」と報告しても、本当にそうかは人間が目視するまで確信できない。

「ドキュメントや Wiki は腐る。でもコンパイラとテストは嘘をつかない（腐ったら落ちる）」。  
ここを割り切って、**決定論的に判定できることはすべてコードと CI に逃がす**のが自分の結論です。

## 2. 自分の運用例: Tripolio の決定論的ガードレール

自分が開発している旅行アプリ **Tripolio**（Flutter + Kotlin/Ktor + Firebase）では、普通なら長大な Skill や Wiki、レビューチェックリストに書きがちな内容を、ほぼすべて「落ちるテスト・自動生成・CI」に置き換えています。

### 2.1 アーキテクチャ・規約・過去バグの再発防止 -> `architecture_test.dart`（約50ルール）

`flutter test` の一部として走る静的解析テスト（965行）で、以下の規約を機械的に強制しています。

- **レイヤー依存の向き**: `domain` は純 Dart、View から Repository / Firebase / 地図 / 写真ライブラリへの直接 import を禁止
- **UDF と型による状態強制**: 画面の状態（`〇〇State`）は必ず `sealed class`、`isLoading` / `isSaving` / `status` のような局面フラグを禁止。View から ViewModel へ呼んでよいのは `.dispatch(...)` のみ
- **デザインシステム強制**: 生の `Color(0x...)`、`TextStyle(...)`、余白・角丸の数値直書きを禁止
- **過去バグの再発防止ルール化**: 例えば「画面の初期化で認証状態を `ref.read` しない（#523）」「`DateTime.now()` の直呼び禁止（`clockProvider` 強制）」
- **本番ビルド汚染防止**: `lib/main.dart` からの import 閉包を辿り、デバッグ用コードが本番に混入しないことを検証
- **ADR の整合性検査**: 1ファイル1レコード、番号重複なし、一覧との一致までテストで検査
- **検出器自体の自己検査テスト**: テストの空振り防止まで含める

### 2.2 仕様書は手で書かない -> コード＆Preview からの自動生成（`docgen`）

画面・デザインの仕様書（`docs/site/`）は **手編集禁止** で、コードと各画面・部品の Preview ゴールデン画像から自動生成します。さらに CI で「doc コメント漏れ」「状態の全 sealed 局面が Preview でカバーされているか」まで検査します。仕様書がコードから乖離しようがありません。

### 2.3 E2E の腐敗すら単体テストで捕まえる -> `e2e_flows_test.dart`

Maestro の E2E フローが参照している画面文言・ID がアプリコードに実在するかを、**PR の単体テスト時点で検査**します。文言変更で夜間の E2E が密かに壊れるのを防ぐ仕組みです。

### 2.4 その結果、AI に渡す自然言語コンテキストは極限まで薄い

決定論的なガードレールを敷き詰めた結果、AI 向けの自然言語ドキュメントは驚くほど薄くなりました。

- `AGENTS.md`: たった **125行**（要点とリンク集だけ）
- `CLAUDE.md`: たった **11行**
- プロジェクト固有の Skill: たった **2つ**（相談・委任用の `tripolio-advisor` と、エミュレータを触って未知の穴を探す探索テスト用の `tripolio-explore` だけ）

しかも AI の探索テストは**「合否判定には使わない」**と明確に役割を分離しています。合否は決定論的テストに任せ、AI は「実装」と「未知の穴探し」という非決定論的な強みだけに集中させる設計です。

## 3. 比較実験: AWS公式 AI-DLC vs 決定論的ガードレール

「そうは言っても本当に差が出るの？」を確かめるため、実際に同じミニアプリで比較実験を行いました。

### 実験条件（フェアネス重視）

藁人形論法にならないよう、A案には自作のなんちゃってワークフローではなく **AWS 公式の [`awslabs/aidlc-workflows` (v2.11.4)](https://github.com/awslabs/aidlc-workflows)** を公式手順どおり導入し、公式の project memory（`aidlc/spaces/default/memory/project.md`）と `.claude/rules/` に規約を記載しました。

- **お題**: 旅行の割り勘・精算ミニアプリ `TripSplit`（React + Vite + TypeScript strict + Vitest）
- **同一条件**: 同一モデル、同一スターター、**完全に1対1で一致する8つの開発規約**
  1. `domain/` は純 TypeScript（React / DOM / Storage 禁止）
  2. View（`*.tsx`）から `data/` や `localStorage` を直接触らない
  3. 状態は Discriminated Union（`isLoading` / `isSettled` / `isOverdue` 等のフラグ禁止）
  4. 現在時刻は `Clock` 注入（`new Date()` / `Date.now()` 直呼び禁止）
  5. View に生の色コード（`#...`）・生 `px` を書かない（`tokens.ts` 強制）
  6. 金額計算（整数円・端数処理）は `domain/` に閉じ込める
  7. View の状態変更は `useReducer` + `dispatch`（UDF）
  8. 仕様書が最新コードと一致していること（A案はドキュメント更新、B案は `scripts/gen-spec.ts` 自動生成＋CI検証）

### 現実の開発を模擬した 4 ステップ

単なる 0 -> 1 の機能追加ではなく、運用で必ず起きるイベントを順番にぶつけました。

- **Step 1（初期実装）**: 旅行グループ作成・メンバー登録・立替記録・均等割り計算・状態遷移（`draft -> open -> settled`）
- **Step 2（仕様変更）**: 均等割りだけでなく「一部メンバー除外」「負担割合（重み）指定」＋理由入力による「精算取り消し（`settled -> open`）」
- **Step 3（規約違反誘発）**: 「精算期限」設定、現在時刻超過時の赤い警告バッジ表示、ローカル永続化・復元・初期化
- **Step 4（並列ブランチ開発 -> マージ）**: 2つの worktree で独立タスク（**4a: CSV エクスポート** / **4b: メンバー別収支サマリービュー**）を同時実装してマージ

## 4. 実験結果

### 4.1 コード 1 行書く前のセットアップ時点で 80 倍の差

| 初期セットアップ指標 | A案（AWS公式 `aidlc` v2.11.4 + 規約） | B案（決定論的ガードレール） |
| --- | ---: | ---: |
| 追加ファイル数 | **398 ファイル**（`.claude/` + `aidlc/`） | **5 ファイル** |
| 追加行数 | **299,775 行** | **366 行** |

さらに、A案で公式の `feature` スコープを起動したところ、この小さな割り勘アプリに対して **全33ステージ・30承認ゲート** が組まれました。また、チェックポイント通過時に人間ターンの返答をフックで必須検証する仕組みのため、自律進行も Stage 1（`intent-capture`）で停止するほど重厚なプロセスでした。

### 4.2 所要時間は +51%、総トークン消費量は 1.91 倍

全 4 ステップ（計 5 タスク）の実測値です。

| ステップ | 所要時間 (A / B) | 総トークン (A / B) | Output (A / B) | ターン数 (A / B) |
| --- | ---: | ---: | ---: | ---: |
| **Step 1（初期実装）** | 418s / 204s (**2.05x**) | 1,590,631 / 405,007 (**3.93x**) | 37,205 / 19,199 | 27 / 13 |
| **Step 2（仕様変更）** | 329s / 277s (**1.19x**) | 907,075 / 715,617 (**1.27x**) | 37,677 / 27,291 | 14 / 15 |
| **Step 3（期限・永続化）** | 403s / 312s (**1.29x**) | 1,430,782 / 886,107 (**1.61x**) | 33,772 / 27,415 | 20 / 16 |
| **Step 4a（CSV出力）** | 246s / 145s (**1.70x**) | 1,040,347 / 542,892 (**1.92x**) | 18,874 / 11,167 | 17 / 13 |
| **Step 4b（収支サマリー）** | 187s / 112s (**1.67x**) | 854,438 / 496,724 (**1.72x**) | 18,544 / 9,947 | 15 / 12 |
| **合計** | **1,583s / 1,050s (1.51x)** | **5,823,273 / 3,046,347 (1.91x)** | **146,072 / 95,019 (1.54x)** | **93 / 69 (1.35x)** |

注目すべきはトークンの内訳です。  
A案は `CacheRead`（毎ターンのコンテキスト再読込）が **516万トークン**（B案 260万トークンの **1.98倍**）、`Output` も **1.54倍** になりました。ドキュメントとルールを読み書きし続けるオーバーヘッドが、そのまま時間とトークンを食い続けています。

### 4.3 人間が向き合うドキュメント量は 20.7 倍、しかも初期文書は化石化

フレームワーク本体（`.claude/`）を除いた純粋なプロジェクト文書を比較すると、以下の通りになりました。

- **A案（`aidlc/spaces/default/`）**: **1,330 行 / 71,012 文字**
- **B案（`AGENTS.md` + `CLAUDE.md` + 自動生成 `spec.md`）**: **66 行 / 3,432 文字**（約 **20.7 分の 1**）

しかも A案では、Step 2〜4 で `requirements.md` や `domain-design.md` を都度書き直す一方で、Step 1 で生成された `aidlc-state.md` や `intent-statement.md` などは更新されず、**コードと食い違った「化石ドキュメント」**として残りました。  
B案は `docs/generated/spec.md` をコードから自動生成し CI（`spec:check`）で最新性を強制するため、乖離は **0件** です。

### 4.4 並列マージで「コードは衝突ゼロなのに、ドキュメント4ファイル全部が衝突した」

今回もっとも象徴的だったのが Step 4（2ブランチ並列開発 -> マージ）の結果です。

- **B案**: `git merge` 一発成功（**コンフリクト 0 件**）。マージ直後の `npm run ci`（型チェック + 全55テスト + アーキテクチャテスト + `spec:check`）も **1.00秒で PASS**。
- **A案**: **`src/` と `tests/`（コード本体）は 1 箇所もコンフリクトせず自動マージできたのに、AI-DLC のドキュメント 4 ファイルすべて（4/4 = 100%）がコンフリクト（計5箇所）してマージが停止しました。**

実際に `requirements.md` で起きたコンフリクトがこちらです。両ブランチが独立して **`FR-8`** を採番したため、真正面から衝突しました（`tasks.md` でも同様に **`Unit 13〜16`** が丸被りしました）。

```diff
<<<<<<< HEAD
### FR-8: 立替履歴・精算結果の CSV エクスポート
- FR-8.1: ユーザーは選択中の旅行グループの「グループ概要」「立替履歴」...
=======
### FR-8: メンバー別収支サマリービュー（立替合計・負担合計・最終収支の比較）
- FR-8.1: 選択中の旅行グループについて、メンバーごとの「立替合計」...
>>>>>>> pattern-a-4b
```

コードは綺麗に疎結合に書けているのに、集中管理されたドキュメントや Wiki が並列開発のボトルネックになる構造が、そのまま実測で再現されました。

### 4.5 正直な発見: 8 規約なら A案も違反 0 件だった - しかし「証明コスト」がまるで違う

最後に、B案で使った `tests/architecture.test.ts`（9テスト）を A案の最終コードに対しても実行し、規約違反のすり抜け件数を機械計測しました。

結果はなんと、**A案も 9/9 PASS（違反 0 件）**でした。

ここはフェアに認めるべきポイントです。最新世代のモデルは、規約が 8 個程度の明快なスコープであれば、自然言語のルールだけでもかなり正確に守れます。

**しかし、本質はその先にあります。**

- A案では、AI が「8規約すべて遵守しました」と自己申告してきても、**本当に守られているかを人間が目視レビューするまで確信できません。**
- 実際、この実験で「A案も違反 0 件だった」と証明できたのは、**B案の `architecture.test.ts` を借りて 350ms で機械検証したから**です。
- そして現実のプロダクト開発では、規約は 8 個ではなく Tripolio のように 50 個以上に増え、何ヶ月も何百 PR も続きます。自然言語の遵守率はコンテキストが増えるほど確率的に落ちますが、決定論的テストは 50 個になっても毎回 350ms で 100% 機械的に落としてくれます。

## 5. まとめ: AI にルールを覚えさせるより、ルールを破れない環境を作る

誤解のないように言うと、AI-DLC のような厳格なプロセスが無意味だとは思いません。監査証跡や承認ゲートが法的に求められる大規模エンタープライズ案件など、ドキュメントのトレーサビリティ自体が成果物になる現場では強い武器になるはずです。

ただ、スピード感を持ってプロダクトを育てていく日々の開発においては、**自然言語のドキュメントや Skill を厚くするほど、時間・トークン・人間の認知負荷・マージコンフリクトという負債が雪だるま式に増えていきます。**

- 規約や設計制約 -> **Skill に書く前に、落ちるテスト（`architecture_test`）にする**
- 仕様書やカタログ -> **Wiki に手書きせず、コードから自動生成して CI で鮮度を守る**
- 過去のバグ再発防止 -> **プロンプトに追記せず、静的テストや回帰テストにする**

こうして決定論的なガードレールで「守るべきこと」を機械に丸投げしてしまえば、人間も AI もドキュメントの番人から解放され、**本当に対応してほしい課題解決・実装・探索に AI のパワーを全振りできる**ようになります。

Skill をもう 100 行書き足す前に、まずは 20 行のアーキテクチャテストを 1 本書いてみるのがおすすめです。
