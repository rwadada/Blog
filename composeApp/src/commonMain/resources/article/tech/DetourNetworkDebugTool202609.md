# ネットワークデバッグツール「Detour」を作った話

普段のAndroidアプリ開発では、Android Studioの Network Profiler で通信を眺めたり、必要ならコード側を書き換えたりするくらいで、通信周りのデバッグは大体事足ります。ただ、たまに「特定のレスポンスだけ一時的に書き換えてクライアントの挙動を確認したい」「DNSスプーフィング的にホストを騙して、まだ手元にしかないサーバーに向けさせたい」といったユースケースが出てきます。

そういう時にはCharlesを利用していました。しかし、そもそも初期設定が難しくてなかなか上手くいかず、せっかく設定できても定期的に何かが壊れるのがかなりのストレスでした。そのため、普段はできる限りCharlesを使わずに済むよう、コード側で無理やり通信内容を書き換えたり、実際の検証環境を用意したりして必死に逃げていました。ただ、ホスト騙しなどの作業だけはアプリ単体ではどうしようもなく、苦肉の策で重い腰を上げてCharlesを開き、そのたびにセットアップの苦しみを味わう……という状態でした。

「このセットアップの苦しみとハマり時間をどうにかしたい」という思いから作ったのが **[Detour](https://github.com/rwadada/Detour)** です。

---

## なぜ作ったか

Charlesの何がストレスだったかを改めて整理すると、こんな感じでした。

- **初期設定が難しく上手くいかない**: SSL Proxyingや証明書の配置、プロキシ設定など、いざ使おうとするたびに設定項目で詰まる
- **定期的に設定が壊れてハマる**: 久しぶりに使うと「なぜか通信が通らない」「どこがおかしいのか分からない」状態になり、毎回一から調査し直す羽目になる
- **たまにしか使わないから使い方を忘れる**: 頻繁に使うツールではないため、触るたびに探り探りになり心理的ハードルが上がり続ける

この「たまにしか使わないのに、使うたびに初期設定や壊れた原因の調査で時間を溶かす」という体験を解消したくて、ターミナルから一発で起動・設定・診断ができるツールを目指しました。

畑違いの技術スタック（CLIツール / TypeScript）だったのですが、「AIコーディングが進化した今なら、畑違いでも自分の手で作れるんじゃないか」と思い立ち、AIと一緒にプロトタイプを組み始めました。土日の2日間で最初の動くプロトタイプができ、そこから継続的に磨き上げていきました。

## Detourとは何か

Detourは、**ターミナルファーストのHTTPデバッグプロキシ**です。`detour start`と打つだけでプロキシが立ち上がり、同時にリアルタイムのWebダッシュボード（`http://localhost:9080`）も起動します。軽い感覚でサクッと使えます。

```bash
brew tap rwadada/detour
brew install detour
detour start
```

一番こだわったのが、あの苦痛だったセットアップ周りです。`detour setup` を打てば、対象デバイス（Android実機、iOSシミュレータ、macOSなど）への証明書インストールとプロキシ設定をほぼ自動で完結してくれます。手動操作が必要な箇所があっても、ターミナル上に「次に何をすればいいか」が分かりやすく表示されます。

```bash
detour setup --target android   # 証明書インストールとプロキシ設定を自動案内
detour doctor                   # 設定が壊れている時に一発で原因を診断
detour cleanup                  # 変更したプロキシ設定を元に戻す
```

特に重宝しているのが `detour doctor` です。ネットワーク環境の変化やProxyのIP変更などで通信が通らなくなった時も、`doctor` 一発でどこがおかしいのか、何を直せばいいのかが即座に分かります。あの一から設定を探し回っていた無駄なハマり時間が完全にゼロになりました。

## 普段のデバッグでどう使っているか

デバッグツールとして色々な機能を詰め込むのではなく、「普段の開発で当たり前に欲しい機能」をストレスなく使えるように作っています。自分が実際のアプリ開発で特に多用しているのは **rewrite** と **mock** です。

### 1. rewrite（通信の書き換え・偽装）
- **レスポンスの一部書き換え**: エッジケースの表示確認や特定フラグの切り替え
- **リクエストの書き換え**: 表示したい特定のデータ（ユーザーIDやパラメータ）に簡易的にアクセスさせる
- **ヘッダーの偽装**: 認証トークンやUser-Agentなどの差し替え

### 2. mock（レスポンスの擬似返却）
- **エラーレスポンスの強制確認**: 500エラーや特定の例外発生時の挙動を、わざわざサーバー側に到達させずに再現
- **開発中APIの先行実装**: サーバー側の実装がまだ届いていない段階で、レスポンスの型を先行して作ってクライアント側の画面開発を進める

## AIコーディングの実践と「エンジニアの役割」

DetourはTypeScript/Reactで書かれていますが、正直コードの大部分は Claude Code 等のAIに作ってもらいました。自分の専門外の技術スタックでも、内容を完全には把握しきれていないままここまで完成度の高いツールが作れてしまったのは本当にすごい体験でした。

ただし、AIに任せっぱなしで破綻しないよう、人間として**最初に厳格なガードレールを敷いたこと**がポイントでした。

- **静的解析とテストの強制**: ユニットテスト・E2Eテスト・型チェック・Lintを整備し、「すべての検証を通らなければ絶対にマージしない」ルールを構築した
- **壊れたらテストで検知**: AIの提案が的外れでも、テストが落ちるので安心してAIにコードを書かせられた

そしてもう一つ感じたのは、**どれだけテストとAI化を進めても、最後の手動動作確認とUI/UXの磨き込みは人間の手が必須である**ということです。テストだけでは拾いきれない細かい挙動の違和感や、操作した時の「手触り感」は、最終的に人間が触って微調整することでしかクオリティが上がらないと痛感しました。

### Rule Engineでモック・書き換え・ブレークポイント

個人的に一番よく使っているのがRule Engineです。`rules.json`にルールを書いておくと、リクエストがマッチした時点で指定したアクションが発火します。

```json
{
  "rules": [
    {
      "name": "mock-users",
      "match": { "method": "GET", "url": "https://api.example.com/users/*" },
      "action": { "type": "mock", "status": 200, "body": { "id": 1, "name": "Mock User" } }
    }
  ]
}
```

アクションは何種類か用意していて、それぞれ用途が違います。

- **mock**: 実サーバーに一切問い合わせずに即レスポンスを返す。「サーバー側の実装がまだないけどクライアント側の画面を先に作りたい」「特定のエラーレスポンス時の挙動を確認したい」という時に便利
- **route**: リクエスト先のホスト/ポートを差し替える。ステージング環境宛のリクエストをローカルの開発サーバーに向け直す、みたいな使い方
- **rewrite**: リクエスト/レスポンスのヘッダーやボディを書き換えて中継する
- **breakpoint**: リクエストをその場で一時停止させ、ダッシュボード上でメソッド/ヘッダー/ボディを手で編集してから再開（あるいは中断）できる

さらにダッシュボードには「Throttle」（帯域制限・遅延・パケットロスのシミュレーション）や「Block Hosts」（特定ホストへの接続を意図的に遮断）もあって、こういう不安定なネットワーク環境でのクライアントの挙動確認もこの上で完結します。ルールセット自体も名前付きで複数保存・切り替えできる「Rule Profiles」があり、stagingと本番挙動確認用を行き来する、くらいの使い方をしています。

### QAの再現作業を、エンジニアもダッシュボードでリアルタイムに追える

想定していたのはこんなシーンです。QAチームが手元の実機で問題を再現している最中に、エンジニアは自分のマシンから同じダッシュボードを開いて、流れてくる通信をリアルタイムに一緒に見られる。`detour start --lan`（または`detour config --lan on`で恒常化）で、プロキシとダッシュボードを`0.0.0.0`にバインドすれば、同じWi-Fi上にいる他のメンバーもそのままダッシュボードにアクセスできます。起動時のバナーやダッシュボードのサイドバーに接続先のURLが並ぶので、共有するIPをいちいち調べる必要もありません。

ただしLAN公開すると同じネットワーク上の誰でもダッシュボードに触れてしまうので、`detour config --dashboard-password <value>`でパスワードを設定できるようにしてあります。

## 1.0.0までのアップデート

0.3.0では、Rule EngineのMock/Rewriteアクションのボディを編集するUIを、ただのtextareaからシンタックスハイライト付きのJSONエディタに置き換えました。長めのJSONペイロードをちまちま手打ちで整形していたのが地味にストレスだったので、これは体感の改善が大きい変更でした。

1.0.0では、これまでCLIのダンプ出力（`--dump full`/`file`）でしかデコードできなかったgRPCメッセージを、`--proto`で読み込んだスキーマを使ってWebダッシュボードのボディビューアでもデコード・整形表示できるようにしました。あわせてメジャーバージョンも1.0.0に上げています（release-pleaseはデフォルトだと1.0未満の`feat:`コミットはマイナーバージョンしか上げない設定なので、`Release-As: 1.0.0`を明示して意図的にメジャーへ上げました）。

ただ、1.0.0を出した同じ日のうちに、0.3.0で入れたばかりのJSONエディタで「10行を超えるとスクロールやカーソルキー操作が効かなくなる」バグが見つかり、1.0.1で直すことになりました。

## AIコーディングの実践の場として

前述の通り、Detourはそもそも「AIがあれば普段の技術スタック（Android/Kotlin）から外れたジャンルでも自分の手で作れるんじゃないか」という思いつきから始まっています。実際、コード量で言うとそこそこの規模のTypeScriptプロジェクト（CLI + Reactダッシュボード）に育ちましたが、実装のかなりの部分をClaude Codeと一緒に進めました。以前書いた「[AIコーディングツールとの付き合い方](AiCodingBottleneck2026.md)」で「計画と骨格は人間、肉付けと検証はAI」という責務分離が現実的だと書いたんですが、Detourはまさにその実践場になっています。

具体的にやっていたのはこんな感じです。

- 機能ごとにIssueを立てて、実装方針の骨子だけ自分で書いてからAIに実装させる
- PRを出したら、GitHub Copilotのレビューを走らせて、指摘があれば都度AIに直させる。CHANGELOGを見返すと"address Copilot review round N"というコミットがひたすら並んでいて、1つの機能に対して5〜10回くらいレビューの往復をしているケースもざらにあります
- リリース作業自体もrelease-pleaseで自動化。コミットメッセージの`feat:`/`fix:`prefixからCHANGELOGとバージョン番号が自動生成され、タグを打つとGitHub ActionsがHomebrewのtap（`rwadada/homebrew-detour`）まで自動更新してくれる

「AIにレビューさせてAIに直させる」を何周も回すのは、最初は「本当にこれで品質担保できるのか？」と半信半疑だったんですが、`npm run verify`（フォーマット・型・lint・依存関係循環チェック・カバレッジ85%以上のユニットテスト・E2Eテストをひとまとめにしたコマンド）をあらゆる変更の後に強制的に通す仕組みにしておいたので、「AIの提案が的外れでも、壊れていればテストが落ちる」というガードレールの中で安心して回せました。個人開発でここまでの検証の仕組みを人力で維持するのは正直しんどいので、AIに書かせる前提でテスト・lint・型チェックを最初から厚めに用意しておいたのが結果的に効いた形です。
