# ネットワークデバッグツール「Detour」を作った話

普段のAndroidアプリ開発では、Android Studioの Network Profiler で通信を眺めたり、必要ならコード側を書き換えたりするくらいで大体のデバッグは事足ります。ただ、たまに「特定のレスポンスだけ一時的に書き換えてクライアントの挙動を確認したい」「DNSスプーフィング的にホストを騙して、手元の開発サーバーに向けさせたい」といったユースケースが出てきます。

そういう場面ではこれまでCharlesを利用していました。ただ、初期設定のハードルが高く、せっせと設定できても久しぶりに使うと定期的に何かが壊れて通信が通らなくなるのが大きなストレスでした。普段はできる限りコード側の書き換え等で逃げていたのですが、ホスト騙しなどの作業だけはアプリ単体ではどうしようもなく、苦肉の策として嫌々Charlesを開いてはセットアップで時間を溶かす...という状態が続いていました。

「この初期設定の面倒くささと、壊れた時のハマり時間をどうにかしたい」という思いから作ったのが、ターミナルファーストのHTTPデバッグプロキシ **[Detour](https://github.com/rwadada/Detour)** です。

---

## Detourとは何か

Detourは、ターミナルから一発で起動できるHTTPデバッグプロキシです。`detour start` と打つだけでプロキシが立ち上がり、同時にリアルタイムのWebダッシュボード（`http://localhost:9080`）も起動します。

```bash
brew tap rwadada/detour
brew install detour
detour start
```

一番こだわったのはセットアップの自動化です。`detour setup` を実行すれば、対象デバイス（Android実機、iOSシミュレータ、macOSなど）への証明書インストールやプロキシ設定をほぼ自動で案内してくれます。

```bash
detour setup --target android   # 証明書インストールとプロキシ設定を自動案内
detour doctor                   # 設定が壊れている時に原因を診断
detour cleanup                  # 変更したプロキシ設定を元に戻す
```

特に重宝しているのが `detour doctor` です。ネットワーク環境の変化やProxyのIP変更などで通信が通らなくなった時も、`doctor` コマンド一発で「どこがおかしいのか」「どう直せばいいのか」が即座に分かります。使い始めるたびに探り探りで原因調査をしていた無駄な時間を解消できました。

## 普段のデバッグでどう使っているか

多機能さを競うのではなく、普段の開発でよく使う機能がストレスなく動くことを重視しています。実際、自分が日常のアプリ開発で特に多用しているのは **rewrite** と **mock** の2つです。

### 1. rewrite（通信の書き換え・偽装）
- **レスポンスの一部書き換え**: エッジケースの表示確認や特定フラグの切り替え
- **リクエストの書き換え**: 表示したい特定データ（ユーザーIDやパラメータ）への簡易アクセス
- **ヘッダーの偽装**: 認証トークンやUser-Agentなどの差し替え

### 2. mock（レスポンスの擬似返却）
- **エラーレスポンスの強制確認**: 500エラーや例外発生時の挙動を、サーバーに到達させずに再現
- **開発中APIの先行実装**: サーバー側の実装を待たずにレスポンスの型を先行作成し、画面開発を進める

## AIコーディングと「エンジニアの役割」

DetourはTypeScript/Reactで書かれており、普段Android（Kotlin）を書いている自分にとっては専門外の技術スタックでした。実装の大部分は Claude Code 等のAIと一緒に進めたのですが、専門外であってもここまで完成度の高いツールを作り切れるのは感動的な体験でした。

一方で、AIに任せっぱなしでコードを破綻させないために、人間として**「最初に厳格なガードレールを敷くこと」**が不可欠でした。

- **静的解析とテストの強制**: ユニットテスト・E2Eテスト・型チェック・Lintを整備し、すべての検証を通らなければマージしないルールを徹底した
- **壊れたらテストで検知**: AIの提案が的外れであっても、テストが落ちるため安心してコードを書かせることができた

また、どれだけテストやAI化を進めても、**最後の手動動作確認とUI/UXの磨き込みは人間の手が必須**だと実感しました。テストでは拾いきれない細かい挙動の違和感や「操作の手触り感」は、最終的に人間が触って微調整して初めてクオリティが上がると痛感しています。

## おわりに

Charlesの初期設定やトラブルシューティングで感じていたストレスと、「AIとガードレールを組み合わせれば専門外のツールも作れるのではないか」という発想から始まったDetourですが、今では自分自身の開発に欠かせないツールになっています。

プロキシツールの設定やハマりどころでモヤモヤしたことがある方は、ぜひ一度試してみてください。

```bash
brew tap rwadada/detour
brew install detour
detour start
```

ソースコードや機能リクエストは [GitHubリポジトリ](https://github.com/rwadada/Detour) で受け付けています。

## 付録: コマンド・オプション概要

全機能やオプションの詳細は [GitHub README](https://github.com/rwadada/Detour) を参照してください。

- **主要コマンド**:
  - `detour start`: プロキシ＆Webダッシュボードの起動
  - `detour setup`: 対象デバイスへの証明書・プロキシ設定の自動案内
  - `detour doctor`: プロキシ接続や証明書信頼の状態を自動診断
  - `detour cleanup`: `setup` で適用したプロキシ設定の復元

- **主な `detour start` オプション**:
  - `--lan`: 同じWi-Fi上の他デバイスからダッシュボード/プロキシへ接続可能にする
  - `--proto <path>`: `.proto` スキーマを読み込み gRPC 通信を自動デコード
  - `--dump <summary|full|file>`: 詳細ログ出力（認証ヘッダー等は自動マスク）
  - `--persist`: ログ履歴を SQLite に保存し過去ログを検索可能にする
