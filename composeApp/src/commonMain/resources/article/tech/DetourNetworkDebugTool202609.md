# detourって名前のネットワークデバッグツール作った話

モバイルアプリを触っていると、「このAPIレスポンス、実際何が返ってきてるんだっけ？」「エラーレスポンスの時の挙動を確認したいけど、サーバー側をわざわざ壊すのは面倒くさいな…」みたいな場面によく出くわします。
そういう時にお世話になるのがHTTPデバッグプロキシなんですが、既存のツールを使っていて「なんかちょっと痒いところに手が届かないな」と感じることが積み重なり、結局自分で作ってしまいました。それが **[Detour](https://github.com/rwadada/Detour)** です。

本記事では、なんでこれを作るに至ったのかという経緯と、実際どんなことができるツールなのかを紹介します。あわせて、以前書いた「[AIコーディングツールとの付き合い方](AiCodingBottleneck2026.md)」で語った内容を、個人開発の場で実践してみた記録としても書いてみます。

---

## なぜ作ったか

HTTP通信のデバッグに使われる定番ツールといえば、Charles ProxyやmitmproxyといったGUI/TUIアプリが有名です。ただ普段使っていて、こんなあたりにモヤモヤを感じていました。

- **GUIアプリだと、普段のターミナル中心のワークフローから浮く**。ちょっとリクエストを確認したいだけなのに、別アプリを起動してウィンドウを切り替えて…という工程が地味に面倒
- **モバイル実機とWebの両方をまたいで使おうとすると、証明書のセットアップや接続確認のたびに毎回同じ手順を踏まされる**。特にAndroidは証明書ピンニングやOSバージョンによる挙動差もあって、「あれ、なんで今回は見えないんだっけ」を都度調べ直す羽目になりがち
- **「このエンドポイントだけ一時的にモックしたい」「ステージングとプロダクションでルールを切り替えたい」みたいな細かい要求に対して、GUI操作だと地味に手数がかかる**

要は、「ターミナルで動かせて、ルールはファイルで管理できて、見る時だけブラウザでリアルタイムに覗ける」というのが自分にとっての理想形でした。既存ツールでも部分的にはできるものの、全部乗せで自分の好みに合うものが見当たらなかったので、「じゃあ作るか」となったのがDetourの始まりです。

## Detourとは何か

Detourは、**ターミナルファーストのHTTPデバッグプロキシ**です。`detour start`と打つだけでプロキシが立ち上がり、同時にリアルタイムのWebダッシュボードも起動します。

```bash
brew tap rwadada/detour
brew install detour
detour start
```

プロキシを経由した通信は、コンソールにログとして1行ずつ流れつつ、`http://localhost:9080`のダッシュボードにも即座に反映されます。HTTPSの中身を見るためのCA証明書も初回起動時に自動生成され、`detour setup`コマンドで対象デバイス（Android実機、iOSシミュレータ、macOS本体など）への証明書インストールとプロキシ設定までまとめて自動化できるようにしてあります。

```bash
detour setup --target android   # adb経由で証明書をpush、Security設定を開いてタップだけで完了
detour doctor                   # 証明書やプロキシ設定がちゃんと当たっているか診断
detour cleanup                  # setupで変更したプロキシ設定を元に戻す
```

ここは実際、一番面倒だった「証明書入れて、信頼設定して、プロキシ向けて…を毎回手作業でやる」部分を機械化したくて作ったコマンド群です。`doctor`は設定が壊れている時に「どこがおかしいか」を教えてくれるので、Android実機であるあるな「証明書は入れたはずなのに何も見えない」を切り分けるのに重宝しています。

## 何ができるのか

### リアルタイムダッシュボードで通信を丸見えにする

プロキシを通った全リクエスト/レスポンスがWebSocketでダッシュボードに流れ込み、テーブルとして一覧できます。仮想化されたテーブルなので大量のログが溜まっても重くならず、メソッドやステータス、URLの部分一致でフィルタできます。行をクリックすればヘッダー・クエリパラメータ・ボディ（JSONは整形表示）をサイドパネルで確認可能です。

「Group by host」でホストごとにグルーピングして畳んだり、気になる2行をCtrl/Cmdクリックしてヘッダー・ボディを横並びでdiffする「Compare」機能もあります。あるリクエストだけ`curl`コマンドとしてコピーしてターミナルで再実行する、といった細かい導線も揃えています。

### Rule Engineでモック・書き換え・ブレークポイント

個人的に一番よく使っているのがRule Engineです。`rules.json`にルールを書いておくと、リクエストがマッチした時点で指定したアクションが発火します。

```json
{
  "rules": [
    {
      "name": "mock-users",
      "match": { "method": "GET", "url": "https://api.example.com/users/*" },
      "action": { "type": "mock", "status": 200, "body": { "id": 1, "name": "Mock User" } }
    }
  ]
}
```

アクションは何種類か用意していて、それぞれ用途が違います。

- **mock**: 実サーバーに一切問い合わせずに即レスポンスを返す。「サーバー側の実装がまだないけどクライアント側の画面を先に作りたい」「特定のエラーレスポンス時の挙動を確認したい」という時に便利
- **route**: リクエスト先のホスト/ポートを差し替える。ステージング環境宛のリクエストをローカルの開発サーバーに向け直す、みたいな使い方
- **rewrite**: リクエスト/レスポンスのヘッダーやボディを書き換えて中継する
- **breakpoint**: リクエストをその場で一時停止させ、ダッシュボード上でメソッド/ヘッダー/ボディを手で編集してから再開（あるいは中断）できる

さらにダッシュボードには「Throttle」（帯域制限・遅延・パケットロスのシミュレーション）や「Block Hosts」（特定ホストへの接続を意図的に遮断）もあって、こういう不安定なネットワーク環境でのクライアントの挙動確認もこの上で完結します。

### Rule Profilesで環境ごとのルールを切り替える

`rules.json`を直接編集するのは開発中は便利なんですが、「stagingで使うルールセット」と「本番挙動確認用のルールセット」を行ったり来たりするようになると手編集がつらくなってきました。そこで、ダッシュボードのサイドバーから名前付きのルールセットとして保存・切り替えができる「Rule Profiles」を追加しました。ドロップダウンから選ぶだけで`rules.json`の中身がまるごと入れ替わり、今どのプロファイルが有効かも常時表示されます。

### スマホ実機からもLANで繋いで見る

`detour start --lan`（または`detour config --lan on`で恒常化）で、プロキシとダッシュボードを`0.0.0.0`にバインドして同じWi-Fi上の他デバイスから繋げられるようにできます。起動時のバナーやダッシュボードのサイドバーに接続先のURLが並ぶので、自分のマシンのIPをいちいち調べる必要はありません。

ただしLAN公開すると同じネットワーク上の誰でもダッシュボードに触れてしまうので、`detour config --dashboard-password <value>`でパスワードを設定できるようにしてあります。カフェの外出先Wi-Fiなど、他の端末が同じネットワークにいる状況で実機確認する時は必須の設定です。

### 地味だけど効く細かい改善たち

0.2.1, 0.2.2あたりは派手な新機能というより、実際に使っていて気づいた細かいバグ修正が中心でした。

- gzip/deflate/brで圧縮されたレスポンスボディを、ダッシュボード表示時に透過的に解凍するようにした（今まで圧縮バイト列がそのまま表示されて読めなかった）
- 新規プロファイル作成フォームが、失敗時に入力内容を保持したまま開いたままになるよう修正
- ルールプロファイルを切り替えた時、`rules.json`がまだ存在しないケースでもちゃんと新規作成されるように修正

こういう「使っていて初めて気づく」類のバグは、実際に自分の開発フローの中でDetourを使い倒しているからこそ拾えているところがあります。

## 気づけば1.0まで来ていた

実はこの記事を書いている最中にも開発は止まらず、0.2.2の次の日には0.3.0、1.0.0、1.0.1と立て続けにリリースが進みました。

0.3.0では、Rule EngineのMock/Rewriteアクションのボディを編集するUIを、ただのtextareaからシンタックスハイライト付きのJSONエディタに置き換えました。長めのJSONペイロードをちまちま手打ちで整形していたのが地味にストレスだったので、これは体感の改善が大きい変更でした。

そして1.0.0で入れたのが、個人的に「これが揃ったらv1と呼んでいいな」と思っていた機能です。もともとDetourの`--proto`オプションはCLIのダンプ出力（`--dump full`/`file`）でしかgRPCメッセージをデコードできず、Webダッシュボードのボディビューアでは生のバイト列のまま表示されるという制約がありました。1.0.0でこの制約をなくし、`--proto`で読み込んだスキーマを使ってダッシュボード上でもgRPCのメッセージボディをちゃんとデコード・整形表示できるようにしています。この機能を「v1にふさわしい目玉機能」と位置づけて、意図的にメジャーバージョンを1.0.0まで引き上げました（release-pleaseはデフォルトだと1.0未満の`feat:`コミットはマイナーバージョンしか上げない設定にしているので、`Release-As: 1.0.0`を明示して意図的にメジャーへ上げています）。

ただ、勢いよく1.0.0を出した同じ日のうちに、0.3.0で入れたばかりのJSONエディタが「10行を超えるとスクロールやカーソルキー操作が効かなくなる」というバグが見つかり、1.0.1で即座に直すことになりました。景気よく大台に乗せた翌日にすぐバグ報告が来るあたりが、個人開発でスピード重視で回している実感そのものだなと思います。

## AIコーディングの実践の場として

Detourは、コード量で言うとそこそこの規模のTypeScriptプロジェクト（CLI + Reactダッシュボード）ですが、実装のかなりの部分をClaude Codeと一緒に進めました。以前書いた「[AIコーディングツールとの付き合い方](AiCodingBottleneck2026.md)」で「計画と骨格は人間、肉付けと検証はAI」という責務分離が現実的だと書いたんですが、Detourはまさにその実践場になっています。

具体的にやっていたのはこんな感じです。

- 機能ごとにIssueを立てて、実装方針の骨子だけ自分で書いてからAIに実装させる
- PRを出したら、GitHub Copilotのレビューを走らせて、指摘があれば都度AIに直させる。CHANGELOGを見返すと"address Copilot review round N"というコミットがひたすら並んでいて、1つの機能に対して5〜10回くらいレビューの往復をしているケースもざらにあります
- リリース作業自体もrelease-pleaseで自動化。コミットメッセージの`feat:`/`fix:`prefixからCHANGELOGとバージョン番号が自動生成され、タグを打つとGitHub ActionsがHomebrewのtap（`rwadada/homebrew-detour`）まで自動更新してくれる

「AIにレビューさせてAIに直させる」を何周も回すのは、最初は「本当にこれで品質担保できるのか？」と半信半疑だったんですが、`npm run verify`（フォーマット・型・lint・依存関係循環チェック・カバレッジ85%以上のユニットテスト・E2Eテストをひとまとめにしたコマンド）をあらゆる変更の後に強制的に通す仕組みにしておいたので、「AIの提案が的外れでも、壊れていればテストが落ちる」というガードレールの中で安心して回せました。個人開発でここまでの検証の仕組みを人力で維持するのは正直しんどいので、AIに書かせる前提でテスト・lint・型チェックを最初から厚めに用意しておいたのが結果的に効いた形です。

## まとめ

「既存ツールに感じてた小さな不満」から始まって、気づけばRule Engineやプロファイル管理、LANアクセス、gRPCデコードまで一通り揃い、v1.0にまで到達した個人開発ツールになりました。似たようなモヤモヤ（GUIが重い、モバイル/Web横断がやりづらい、環境ごとのルール切り替えが面倒）を感じたことがある方には、一度試してみてもらえると嬉しいです。

```bash
brew tap rwadada/detour
brew install detour
detour start
```

ソースやCHANGELOGは[GitHubリポジトリ](https://github.com/rwadada/Detour)に置いてあるので、気になった方はそちらもどうぞ。今後もissueベースで機能追加やバグ修正を続けていく予定です。
