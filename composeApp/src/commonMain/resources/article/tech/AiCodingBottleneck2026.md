# AIコーディングツールとの付き合い方、現時点での個人的な所感

最近のAIの進化が早すぎて、置いていかれないようになんとか向き合ってる今日この頃です。  
ちょっと前までは「簡単なボイラープレートを書いてくれる便利な子」だったのが、今ではエージェント機能を使って新機能を実装させることも見聞きするようになってきました。

自分も日々の開発でAIを活用しながら、「AIコーディングって実際どう付き合うのが一番いいんだろう？」とあれこれ検証・検討しています。  
その中でなんとなく見えてきた、AIを使ったコーディングの「現実的な付き合い方」と「課題」について、客観的なデータや論文、公式の設計ガイドラインなどを交えつつ、メモ代わりにまとめてみます。

---

## 1. コスト無制限なら「完全丸投げ」もアリ

まず、「AIに最初から最後まで全部作ってもらう（丸投げ）」というアプローチについて。

もし予算やトークン数、そして実行時間に **まったく制約がない** のあれば、これは大いにアリだと思います。  
要件を雑に投げて、AIが勝手に動き、動かない箇所を自己修正しながら動くコードを作り上げるのを待つ、というAIを使った開発と言って思い浮かべる形なんじゃないかなーと思います。

ここでいう「コスト」なんですが、AIのAPIトークン代やサブスク代がどれだけ高騰しようが、 **人間のエンジニアが手を動かしたときの人件費** と比較すれば、相対的には圧倒的に安いというのは確かだと思います。  
加えてAIは、人間と違って「10個のタスクを同時に並列で走らせる」といったスケールも容易です。この並列性と金銭的コストの低さはAIの最大の強みだろうと感じます。  
一方で、これは逆に「人間がレビューすべきPull Requestが一瞬で10倍に増える」ということで、後述している人間の認知のボトルネックを作成する原因になります。

実際に実行してみる場合、この「丸投げ方式」に自分は以下のような課題に直面しました。  
それは、　**完成度を磨くための検証・デバッグのコストが無尽蔵にかかる**　という点です。

特に新規の設計や、既存システムのリアーキテクチャ（アーキテクチャ刷新）のタイミングにおいて、この問題は顕著になる感覚があります。

1. AIが「とりあえず動くけど設計的に破綻しているコード」を生成したとする。
2. それを実用レベルのクオリティに磨き上げるためには、テストコードを書き、エッジケースを検証するための「検証環境」を用意しなければならない。
3. しかし、その検証環境の設計自体が不適切だったり、検証のためのコード自体にバグがあったりすると、AIはそのバグを解消するために迷走し始める。

人件費より安いとはいえ、AIが無限ループのように迷走し始めると、修正のためのリトライ時間や、「AIの出力のどこが間違っているのかをデバッグする人間の認知コスト（レビュー工数）」が無尽蔵に消費されていくことになります。
（昨今話題の、AI自身にテストとデバッグを自律的に繰り返させる「ループエンジニアリング」や、役割の異なる複数のAIをグラフ構造で繋いでワークフローを制御する「グラフエンジニアリング（フローエンジニアリング）」は、まさにこの「AIの迷走」をシステム側で自動制御し、人間の脳の負担（認知コスト）を減らすためのアプローチなんだろうなと思ったり）

実際、ソフトウェア開発リサーチ企業である **GitClear** が2023年から2026年にかけての6億2300万行以上の変更コードを対象に実施した、最新の調査「[The Maintainability Gap: AI Code Quality in 2026](https://www.gitclear.com/the_ai_code_quality_maintainability_gap)」では、AI普及に伴うコード品質への深刻な「下向きの圧力」が実測データとして示されています。

| コード品質の評価指標 | 2022年比での変化（2026年実測値） | 開発コードベースへの影響 |
| :--- | :--- | :--- |
| **リファクタリング** | 70% 減少 | healthyなコード再利用性が著しく低下 |
| **コード重複** | 81% 増加 | コピペコードが量産され、DRY原則が崩壊 |
| **コミット内のコピペ** | 41% 増加 | その場しのぎの実装コードが急増 |
| **エラーマスキング** | 47% 増加 | バグを隠蔽するコードが増え、デバッグが困難に |
| **長期的メンテナンス性** | 74% 減少 | レガシーコードとしての負債蓄積スピードが加速 |

AIはDRY（Don't Repeat Yourself）原則を無視して重複したコードを量産する傾向があり、丸投げでスピードを上げたつもりが、長期的にはメンテナビリティの低下や検証コストのインフレを引き起こしてしまう事に繋がります。

## 2. AIと人間の「最適な責務分離」

具体的に人間とAIのタスクをどう分けるのが最も効率的なのか？

いくつか試してみた結果から共有します。
たとえば、テストハーネス（検証環境）をガチガチに強化した上で、AIに「実装の前にまず設計ドキュメントを書かせ、人間がそれをレビューする」というアプローチ。あるいは、AIに「対話形式で人間に質問を投げさせ、仕様の曖昧さを潰してから実装に移らせる」といったアプローチです。
（いわゆる、AIを各プロセスに組み込んで自律的に連携させる「AI-DLC（AIソフトウェア開発ライフサイクル）」や、コードを書く前にまず仕様（Spec）を定義してAIに落とし込む「SDD（仕様駆動開発）」と呼ばれるアプローチに近い形です）

これでより堅牢な実装ができるかと思ったものの、別の問題が発生しました。 **「レビューの対象となるドキュメント数や質問項目が増えると、人間の認知の限界を容易に超えてしまう」** という事です。
大量のAI製ドキュメントを読み込んで確認したり、AIからの質問攻め（対話）に一つずつ脳のリソースを使って答えていくのは、思った以上にエネルギーを消耗し、疲弊します。（実際、後半に行くにつれて、深く考えずに承認することは体感増えていった気がします）

この「AI製ドキュメントの査読」や「AIとの対話」が人間を疲弊させる現象は、近年のHCI（Human-Computer Interaction）分野の[先行研究（Microsoft Researchの調査レポートなど）](https://www.microsoft.com/en-us/research/publication/generative-ai-in-real-world-workplaces/)でも **「レビュー疲れ（Review Fatigue / Vigilance Decrement）」** や **「エージェント調整オーバーヘッド（Agent Coordination Overhead / Interaction Overhead）」** として明確に指摘されていました。

* **意図の逆構築（Reconstructing Intent）の負荷**: 人間同士のレビューと異なり、AIが書いたコードやドキュメントを評価する際に、人間は「自分が設計していない未知のロジックから、AIの意図を逆算して組み立て直す」必要があり、これが脳に膨大な認知的負荷を与えます。結果として、ある限界を超えると人間は深い検証を諦め、表面的なチェックでパスしてしまう現象（Vigilance decrement）が確認されています。
* **調整コスト（Coordination Overhead）の爆発**: AIに仕様を考えさせたり対話で質問攻めにさせると、人間側に「仕様決定のための文脈切り替え（Context Switching）」やデバッグ、もっともらしいが間違っているAIの回答の検証が頻発し、人間側のエネルギーが急速に消費されてしまいます。
* **速度の非対称性（Asymmetry of Speed）**: AIの圧倒的な出力スピードと、人間側の検証・理解スピードの間にある決定的なボトルネック。

コンテキストの肥大化による「情報埋没」については、AI自身の仕様としても同様のボトルネックがあります。

つまり、AIに「計画（ドキュメント作成）や対話」を委ねて人間が「レビュー・検証」に回るスタイルは、人間の認知的な限界というボトルネックに直面するということが実感としても研究結果からもわかります。

このことから、現時点で最も「人間の負荷」と「AIの成果物の品質」のバランスが良いと感じている **責務の分離** が以下の形です。

* **計画（設計方針）と「ラフな実装（骨格）」は人間がやる**：
    システム全体の設計や仕様の方向性、構造（インターフェースや大枠の構造）は、AIのサポートを適宜借りつつも、**人間が主導して自分の手で書き上げる**。
* **詳細な実装（肉付け）と「受け入れ条件での検証」はAIにやらせる**：
    骨格に対して具体的なコードを肉付けしていく詳細実装や、事前に定義した「受け入れ条件」を満たしているかのテスト・検証は、**AIに丸投げします**。

この役割分担がなぜ良いかというと、**手戻りと人間の対話・査読コストを最小限に抑えつつ、AIの圧倒的な速度を活用できるため** です。

人間が先に「計画と骨格」というガードレールを用意することで、AIの迷走や対話による認知負荷の上昇を防げます。その上で、時間のかかる「詳細実装とテスト（受け入れ検証）」をAIにやらせることで、AIの生産性と並列性のメリットを得られると感じてます。

「人件費対比での安さ」と「並列処理の強さ」をこの検証部分で活かしつつ、人間は最も付加価値の高い「計画と骨格作り」にリソースを集中する。これが、現時点で自分が辿り着いた付き合い方だと思っています。

## 3. 「既存コードの統一感」が成果物のクオリティを左右する

AIをサポーターとして使うにあたって、もう一つよく遭遇する課題があります。  
それが **コンテキストの引きずられ問題（Lost in the Middle / Contextのノイズ）** です。

モデルのコンテキストウィンドウが広くなり、大量の関連ファイルを読み込めるようになったのは良い事ですが、何でもかんでも無闇に読み込ませると、かえって重要な指示や方針が埋もれてしまう（いわゆる「Lost in the Middle」）問題が発生します。  
（論文「[Lost in the Middle: How Language Models Use Long Contexts](https://arxiv.org/abs/2307.03172)」でも示されている通り、LLMは入力の「最初」と「最後」の情報は拾いますが、「中間」にある情報は無視されがちです）

この挙動への対策として、[Anthropicの公式 Prompt Engineering ドキュメント（Long Context Tips）](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/long-context-tips)では、以下のようなベストプラクティスが推奨されています。

* **指示（プロンプト）はコンテキストの最後に配置する**: 大量のデータ（既存コードなど）を先に流し込み、本当に守らせたい指示や規約をプロンプトの最末尾に置くことで、情報の埋没を防ぐ。
* **XMLタグによる構造化**: `<context>`や`<rules>`といったXMLタグを使って入力情報を明示的に区分けする。

ただ、どんなにプロンプトを構造化したところで、プロジェクト内の既存コード（実態）と指示された規約（理想）の間に統一感がなかったり、矛盾があったりすると、AIは実態に引きずられて混乱します。  
自分自身、既存のモバイルアプリ（XMLベースの古いレイアウト）をJetpack Composeに置き換える移行作業をした際、この現象を体験しました。

- 既存のレガシーロジックや古い書き方に引きずられ、AIが想定外の挙動をするコードを吐き出してしまう。
- 規約を読ませても、目の前にあるコードベースに古いパターンが散見されると、AIはどちらを信じるべきか判断できずに破綻する。

逆に、 **似たような画面を、あらかじめ人間が手動で1画面だけでも綺麗にCompose移行して『お手本』を作っておいた** ケースでは、AIの出力はかなり優秀でした。

これは[OpenAIの公式 Prompt Engineering ガイド](https://platform.openai.com/docs/guides/prompt-engineering)で推奨されている、**リファレンステキストの提供（Provide reference text）** や **Few-shotプロンプティング（例示による指示）** そのものです。  
OpenAIのガイドでも、モデルが推測で誤ったコードを書く（ハルシネーションを起こす）のを防ぐ最も強力な方法として、「手本となる参考テキストを直接与えること」が挙げられています。

最近のAIツールは周辺のファイルを自動でインデックスしてコンテキストに含めるので、「統一感のある綺麗な既存ロジック」は最強のFew-shot（リファレンステキスト）として勝手に機能してくれます。規約をくどくど文字で説明するよりも、目の前のお手本を見せる方が、圧倒的に正確で同じ設計思想に沿った綺麗なコードを出力してくれるわけです。

つまり、AIに良いコードを書かせるための最大の要素は、小手先の指示文ではなく、**すでにリポジトリ内にある統一感のある、綺麗なコードベースそのもの** です。

## 4. 生産性は本当に上がったのか？

ここまでAIの使い方について書いてみたんですが、そもそも「AIによって開発全体の生産性は上がっているのか？」という点については、個人的にはとても懐疑的です。
ありませんか？AI活用してるはずなのに、なんか最近レビュー負荷高いなとか、QA詰まってるな？とか
そうです。「コードの行数が増えるスピード」や「タイピングの手間」という観点で見れば、生産性は間違いなく数倍になっています。  
一方で、「リリースサイクル」や「プロダクトの価値向上」という大きな視点で見ると、意外とそこまでの変化は起きていないように見えます。

これは、**ボトルネックが移動しただけ** だからだと考えています。

プロジェクトによりけりだと思いますが、元来存在した、構文を調べたり、タイピングしたり、ボイラープレートをセコセコ書いたりするソフトウェア開発の「コードを書く」作業のボトルネック。
ここが、AIの登場によって超高速化された結果、新たなボトルネックが浮かび上がってきました。

- **仕様の言語化・言語による正確な設計（プロンプティング／コンテキストコントロール）**
- **AIが生成したコードのレビューと動作検証**
- **そもそも「何を解決すべきか」という要件定義の妥当性**

| 開発フェーズ | 従来の開発フロー | AI導入後の開発フロー |
| :--- | :--- | :--- |
| **要件定義・設計** | 人間が脳内で時間をかけて行う | 人間が主導（AIと対話してドメインを言語化） |
| **コード実装** | **【従来のボトルネック】**<br>人間が構文を調べて手書きする（時間がかかる） | **【超高速化】**<br>AIが一瞬で大量生成（タイピング不要） |
| **レビュー・検証** | 人間同士で Pull Request をレビューする | **【新たなボトルネック】**<br>大量のAIコードを人間が徹底検証（認知負荷が激増） |

たとえAIが1秒で100行のコードを生成してくれても、それを人間がレビューして「本当に仕様通りか？」「エッジケースでバグらないか？」を検証するのには、それ相応の時間がかかります。

実際、これを裏付けるデータも出ています。  
[New Relicが発表した調査レポート（State of AI Coding 2026）](https://newrelic.com/jp/resources/white-papers/ai-coding-report-2026)によると、AI生成コードを本番環境へデプロイした後に、 **78%の組織が「本番障害（インシデント）が増加した」** と回答しています。さらに、 **82%** の組織が過去6ヶ月の間にAI生成コードに起因する本番障害を少なくとも1回以上経験しており、人間による事前の検証なしに本番リリースされている割合は **62%** に達しているとのこと。

AIが大量のコードを瞬時に生成できるようになった結果、人間のレビューや検証能力を超えた「バグを含んだコード」がコードベースに混入し、かえって障害対応という泥沼の渋滞（ボトルネック）を引き起こしている。  
これがまさに、「ボトルネックの移動」を象徴してるんじゃなかろうかと感じます。

## 5. レビューに人間はどこまで関与すべきか？

最近はSNSなどで「AIだけで個人開発して、3日でサービスをリリースしました！」といった声をよく耳にします。  
正直なところ、いちエンジニアとしては「よく中身（特にエッジケースや依存関係）を徹底検証せずに本番リリースできるな…」と、恐怖半分、純粋な感嘆半分で眺めています。  

実際問題、ユーザーに責任を持つプロダクト開発や、ある程度規模のあるリポジトリで開発する以上、「えいや」で出すわけにはいかず、一定成果物の正しさを担保する必要があると思います。
そこで出てくるのが、**そもそも、本当にAIの書いたコードを人間がすべてレビューすべきなのか？** という話です。

これに関しては、スタンフォード大学が2023年に発表した論文「[Do Users Write More Insecure Code with AI Assistants?](https://arxiv.org/abs/2211.03622)」が、面白い人間の認知バイアスについて報告しています。

* **AI使用による脆弱性の増加**: AIアシスタントを使用した開発者は、使用しなかったグループに比べて、セキュリティ脆弱性のあるコードを書く確率が有意に高かった。
* **「過信（Overconfidence Gap）」の発生**: それにもかかわらず、AIを使用した開発者は「自分のコードは安全である」と **過剰に信用（過信）してしまう** 傾向（False sense of security）があった。

「AIが書いたものだから大丈夫だろう」という無意識のバイアスが働き、人間のレビューの目をすり抜けやすくなるリスクを示しています。

一方で、Googleが公開している公式の[コードレビューガイドライン（eng-practices）](https://google.github.io/eng-practices/)では、レビューの品質と開発速度を保つために「1つの変更（CL）は小さく保つこと（目安として約100行、1,000行は大きすぎる）」が強く推奨されています。CLを小さく保つことで、レビュー側の疲労（Review fatigue）を防ぎ、バグの見逃しを減らすためです。

しかし、AIは一瞬で何百行, 何千行ものコードを出力します。これらをそのままレビューしようとすると、レビューアは疲弊し、見逃しが多発するのは必然ですよね。

なので、個人的な解決策としては、**AIによる自動レビューゲートを前提としつつ、影響範囲の大きさに応じて人間のレビューの厚みを変える** というハイブリッドなアプローチが現実解だと考えています。

その上で重要なのは、単にAIに「このプルリクをレビューして」とざっくり頼むだけではレビュー品質にブレが出ることです。  
そこで最近効果的だと感じているのが、**ドメインや観点別に特化したレビュー用AIエージェント（あるいはAIのSkill）を定義し活用すること** です。

たとえば、
- 事業価値や技術負債の観点からコードを評価する **CPO（Chief Product Officer）エージェント**
- UX・仕様整合性・バグリスクに特化した **PO（Product Owner）エージェント**
- 特定の技術スタック（KotlinやCompose等）の専門家として技術的な妥当性を検証する **Techエージェント**

といった役割別のエージェントをCI等に組み込み、自動レビューを走らせるアプローチです。  
これによって「AIの書いたコードをAI自身が多角的に自動レビューする」という前処理の精度を高めることができます。

その上で、人間の介入度を傾斜配分します。
- **影響範囲が極めて小さく、安全な領域**（UIの表示修正、隔離されたユーティリティ関数の追加など）：  
  上記の複数AIエージェントによるダブルチェックと自動テストのパスだけでOKとし、人間のレビューは最小限（あるいはパス）にする。
- **システムの根幹に関わるクリティカルな領域**（決済、認証、コアなデータフローや共通モジュールなど）：  
  人間が設計思想からエッジケース、パフォーマンスへの影響まで、徹底的に厚みを持たせてレビューする。

とはいえ、この **影響範囲の判断（どれが本当に安全で、どれがリスクを孕んでいるか）を見極めること自体が非常に難しい** という話もあります。

AIが「一見完璧に動くコード」を出力したものの、実はバックグラウンドで予期せぬ広範囲な依存関係に影響を及ぼしていた…といったケースを、レビューを省略して見逃せば、前述した「深刻な障害発生」に直結します。

結局、この「レビューの厚みをコントロールするための判断コスト」や「影響範囲の見極め」自体が、新たな人間の認知負荷（ボトルネック）として存在するのが現状ですね。  
この課題を乗り越えるには、「この重要ディレクトリ以下のファイル変更は必ず人間がレビューする」「それ以外は自動テストとAIセルフチェックで通す」といった、ルールによる機械的な傾斜配分をあらかじめ敷いておくのが、現実的な落としどころかもしれないです。（正直まだここは探り中）

## まとめ

AIを使ったコーディングは、使い方次第で天国にも地獄にもなります。

- **無計画な丸投げ**は、検証・障害対応コストを増大させるため避けるべき（インシデント増加78%の罠）。
- **既存コードの統一感**を維持し、良質な「お手本」をFew-shotとして活用する。
- **サブエージェント（Sub-agents）による自動レビュー**を導入し、人間がレビューすべき箇所を絞り込む。
- **賢いサポーター利用**こそが、現状のエンジニアにとって最も価値を引き出せる使い方。
- **レビューの傾斜配分**が不可欠。影響範囲の見極めこそが次世代のスキルとなる。

これからもAIツールは進化し続けると思いますが、AIにコードを書かせるのが上手い人というのは、結局のところ **自分で綺麗な設計ができて、かつそれを正確に言語化して伝えることができる人** なんだとしみじみ感じています。
