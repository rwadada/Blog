# Blog 記事作成スキル

アイデアの種を壁打ちで育て、記事として公開可能な状態（PR作成）まで持っていく。
リポジトリの構造・登録方法の詳細は `references/repo-structure.md` を参照（Phase 3 以降で必ず読むこと）。

## 全体フロー

0. **出し先チェック** — Zenn かこのブログか、目的から判定する
1. **壁打ち** — アイデアを深掘りし、読者と切り口を定める
2. **構成合意** — アウトラインを提示し、合意してから書く
3. **執筆** — 既存記事のトーンに合わせて Markdown を書く
4. **デモ実装** — 効果的な箇所にインタラクティブな Composable デモを差し込む
5. **繋ぎこみ** — BlogItems.kt に登録（ルーティング・一覧・検索は自動反映）
6. **検証 → commit & draft PR**

途中で作業を引き継ぐ場合（例:「昨日の記事の続き」）は、該当フェーズから再開してよい。

## Phase 0: 出し先チェック（Zenn か、このブログか）

このブログと Zenn は役割が違う。**Zenn = 反応検証と販売のチャネル**（トレンド・いいね・ブックマークという
計測可能な反応があり、有料本の決済導線につながる）、**このブログ = 名刺・ポートフォリオ**（CMP/Wasm 製である
こと自体が実績で、動く Compose デモという Zenn に無い武器を持つ）。書き始める前に記事の目的から出し先を判定する。

| 記事の目的・性質 | 出し先 |
|---|---|
| マネタイズの反応検証 / 有料本（Zenn 本等）への導線 / 広いリーチ・SEO が主目的 | **Zenn** — このスキルは使わない |
| インタラクティブな Compose デモで価値が増す / 体験ベースの語り / ポートフォリオ・名刺目的 | **このブログ** — Phase 1 へ続行 |
| 両方に価値がある | **書き分け** — Zenn に本編、このブログに別切り口（デモ付き）。Zenn は canonical URL 非対応のため、完全な二重投稿はしない |

- 判定が Zenn の場合: 理由を一言添えて Zenn での執筆を案内し、このスキルを終了する
  （Zenn は zenn-cli + GitHub 連携の別リポジトリ管理であり、このリポジトリでは扱わない）
- 迷う場合は一問だけ聞く: 「この記事の目的は**検証・販売**ですか、それとも**資産・名刺**ですか？」
- ユーザーが出し先を明示している（「ブログに書きたい」「Zenn 用に」等）ならこのフェーズはスキップする

## Phase 1: 壁打ち

記事の質は書き始める前の解像度で決まる。アイデアを受け取ったら、すぐ書き始めずに対話で深掘りする。

- 質問は一度に 2〜4 個まで。尋問にならないよう、自分の理解や仮説を添えて投げる
- 掘るべき観点: **誰に読ませたいか**(想定読者の前提知識)、**何が新しいか**(既存記事や世間の解説との差分)、
  **実体験・具体例はあるか**(このブログの記事は体験ベースの語りが核になっている)、
  **結論・主張は何か**(「〜してみた」系でも学びの一文がある)
- ユーザーの回答が薄い観点は、こちらから選択肢や仮説を出して反応をもらう方が速い
- アイデアが最初から具体的（構成まで頭にある様子）なら、深掘りは 1 往復に留めて構成合意へ進む

## Phase 2: 構成合意

壁打ちの内容をアウトライン（見出し案 + 各セクション 1〜2 行の要旨 + デモ挿入候補箇所）にまとめて提示し、
合意を得てから執筆に入る。ここで手戻りを潰すのが目的なので、「この構成で書きます」ではなく
変えてほしい点を聞く形で出す。タイトル案も 2〜3 個併記する。

## Phase 3: 執筆

書く前に必ず既存記事を 1〜2 本読んでトーンを掴む（`composeApp/src/commonMain/resources/article/tech/` の日付が新しいもの。
例: `BlogUpdate2026.md`, `ComposeArchitecture202602.md`）。特徴:

- 日本語・です/ます調ベース。堅すぎず、たまに砕けた本音（「めっちゃメンテ大変だったから〜」）が混ざる
- 1 行目は `# タイトル`、直後に導入 2〜3 段落、以降 `## セクション`
- コードブロックは言語指定付き。表・リスト・リンクは標準 Markdown
- 画像は `images/ファイル名` で参照（実体は `composeApp/src/commonMain/resources/images/`）。
  ユーザーから素材をもらう必要がある場合はプレースホルダーを置いてその旨を明示する

ファイルは `composeApp/src/commonMain/resources/article/tech/<Slug>.md` に置く。
Slug は PascalCase + 必要なら年月サフィックス（例: `ComposeArchitecture202602`）。
**Slug がそのまま URL・ルーティングのキーになる**ので、公開後に変えない前提で命名する。

執筆後、本文をユーザーにレビューしてもらう。修正の往復はここで済ませる（PR 後の直しより安い）。

## Phase 4: インタラクティブデモ実装

このブログの特色は記事内で動く Compose デモ。文章より動きで伝わる箇所（アーキテクチャの流れ、
アニメーション、比較表など）があれば実装を提案する。無理に入れる必要はない — 静的な記事も普通にある。

仕組み（詳細は references 参照）:

1. Markdown 内の挿入位置に `%%%_COMPOSABLE_INJECT_SLOT_%%%` を単独行で置く
2. デモ Composable を `feature/common/src/commonMain/kotlin/` に実装（既存の `ArchitectureDemo.kt` や
   `PackageStructureDemo.kt` が良い手本。パッケージ宣言なしのルートパッケージ）
3. BlogItem の `composableItems` にマーカーの登場順と同じ順序で登録する

注意: **material-icons は使えない**（現行 Kotlin/Wasm と非互換）。アイコンが要る場合は
`NavigationIcons.kt` のように ImageVector を手書きするか、テキスト・図形で表現する。

## Phase 5: 繋ぎこみ

`feature/common/src/commonMain/kotlin/BlogItems.kt` の `blogItems` リスト**末尾**に追加する
（一覧は `reversed()` で表示されるため、末尾 = 最新として先頭に出る）。

- `path`: `article/tech/<Slug>.md`
- `date`: 今日の日付 `YYYY-MM-DD`
- `type`: `BlogItem.Type.TECH`（詳細ページがあるのは現状 TECH のみ）
- `summary`: 記事の要約 3〜4 文。検索対象かつ一覧カードに表示されるので、記事の核心と読みどころを書く

これだけで詳細ページへのルーティング（`Route.TechArticle(slug)`）、Tech 一覧、Home の Recent Posts、
検索のすべてに自動で載る。ナビゲーションコードの手書きは不要。

## Phase 6: 検証 → commit & draft PR

1. `./gradlew build` が通ることを確認（デモ実装がある場合は特に）
2. 可能なら `./gradlew wasmJsBrowserDevelopmentRun` で起動し、一覧表示 → 記事遷移 → デモ動作を目視確認するようユーザーに促す
3. ブランチを切って記事・デモ・BlogItems.kt をコミットし、draft PR を作成
   （PR 本文に記事タイトル・概要・確認方法を書く）

公開判断はユーザーが PR 上で行う。main への直接 push はしない。
